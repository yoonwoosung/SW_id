## 상황

초기 백엔드는 약 1,577줄의 단일 `app.py`에 모델·라우트·비즈니스 로직·외부 API 호출이 모두 섞여 있었다. 백엔드 개발자 2명이 같은 파일을 동시에 수정해 커밋마다 충돌이 발생했고, 추천 로직 등이 라우트 함수 안에 인라인으로 있어 재사용·테스트가 어려웠다.

## 결정 기준

- 유지보수성(관심사 분리)
- 협업(동시 작업 시 충돌 최소화)
- 개발 속도(기존 동작을 깨지 않고 점진 적용)
- 테스트 용이성

## 검토한 대안

### 대안 1: 단일 파일 유지 + 함수 정리만

- 설명: 파일은 그대로 두고 함수 순서·주석만 정리.
- 장점: 변경 위험이 가장 작다.
- 단점: 동시 작업 충돌·재사용 문제를 근본적으로 해결하지 못한다.

### 대안 2: Flask Blueprint로 도메인 분리

- 설명: 표준 Blueprint로 라우트를 도메인별로 분리.
- 장점: Flask 관례에 부합.
- 단점: 엔드포인트 이름이 `blueprint.endpoint`로 바뀌어 24개 템플릿의 모든 `url_for(...)`를 수정해야 한다 → "위치만 이동, 동작 불변" 원칙과 충돌.

### 대안 3: 도메인 패키지 + register(app) 등록

- 설명: `models/ routes/ services/ external/ common/`으로 파일을 나누되, 라우트는 `app.add_url_rule`로 **기존 엔드포인트 이름을 그대로** 등록.
- 장점: 템플릿 무수정, 동작 100% 보존, 관심사 분리 달성.
- 단점: 진짜 Blueprint가 아니라 커스텀 등록 패턴이라 Flask 표준과 약간 다르다.

## 결정

**대안 3을 선택했다.** 도메인 패키지로 분할하고, 라우트는 `register(app)` + `add_url_rule`로 기존 엔드포인트 이름을 유지했다.

## 선택 이유

기존 화면·동작을 그대로 유지하면서(템플릿 24개 무수정) 협업·재사용 문제를 해결할 수 있는 유일한 방식이었다. 엔드포인트 이름 보존이 이번 리팩터의 핵심 제약이었다.

## 긍정적인 결과

- `app.py` 1,577줄 → 약 85줄(설정·배선만).
- 백엔드 2명이 서로 다른 파일을 만지게 되어 충돌이 줄었다.
- 추천 로직이 services로 빠져 단위 테스트가 가능해졌다.

## 부정적인 결과

- 진짜 Blueprint가 아니라 커스텀 등록 패턴이라, Flask 표준 문서와 1:1로 매칭되지 않는다.
- 파일 수가 늘어 초기 탐색 비용이 약간 증가한다.
