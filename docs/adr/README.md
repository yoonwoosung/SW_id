# ADR (Architecture Decision Record)

ADR은 프로젝트의 **중요한 기술적 결정**과 그 이유·대안·결과를 기록하는 문서다.

## 목적

- 나중에 "왜 이렇게 했지?"에 답할 수 있게 한다.
- 새 팀원이 맥락을 빠르게 이해하게 한다.
- 포트폴리오에서 기술 선택 근거의 출처가 된다.

## 작성해야 하는 상황(예시)

- 시스템 아키텍처 변경, 멀티모듈/패키지 구조 선택
- 데이터베이스 선택, 캐시·메시지 큐 도입
- 인증 방식 선택, 배치와 실시간 처리 방식 선택
- 외부 API 연동 방식, 파일 저장 방식, 배포 구조
- 데이터 정합성 보장 방식
- 중요한 라이브러리·프레임워크 선택

## 작성하지 않아도 되는 상황

- 단순 클래스/변수 이름 변경
- 작은 버그 수정
- 일반적인 CRUD 추가

## 파일 이름 규칙

```text
NNNN-제목-슬러그.md      예: 0001-app-domain-split.md
```

- `NNNN`: 4자리 일련번호(0001부터 증가)
- 제목은 영문 소문자 케밥케이스

## 상태 관리

`제안 → 승인 → (필요 시) 대체됨 / 폐기됨`

- **제안**: 논의 중
- **승인**: 결정되어 적용
- **대체됨**: 더 새로운 ADR이 이 결정을 대체
- **폐기됨**: 더 이상 유효하지 않음

## 기존 ADR 수정 기준

- 승인된 ADR의 **결정 내용은 사후에 바꾸지 않는다**(역사 기록).
- 오탈자·링크 보정 정도만 수정한다.
- 결정이 바뀌면 **새 ADR을 만들고** 이전 ADR의 상태를 `대체됨`으로 바꾼 뒤, 서로의 헤더(`대체하는 ADR` / `이 ADR을 대체한 ADR`)를 링크로 연결한다.
