# 팀 개발 워크플로

FarmLink 팀의 개발 기록은 다음 흐름으로 관리한다.

```text
Issue 생성 → 브랜치 생성 → Commit → Pull Request
→ 코드 리뷰 및 병합 → (중요한 결정은) ADR 작성
→ 주간 Worklog 정리 → 프로젝트 종료 시 포트폴리오 추출
```

각 기록의 역할은 서로 겹치지 않는다.

| 기록 | 역할 |
|---|---|
| Issue | 무엇을 해결할 것인가 |
| Commit | 무엇을 변경했는가(짧게) |
| PR | 무엇을 어떻게 왜 변경했는가 |
| ADR | 왜 그 기술적 선택을 했는가 |
| Worklog | 이번 기간에 어떤 중요한 일이 있었는가 |
| Portfolio | 그 경험으로 어떤 역량을 증명하는가 |

---

## 작업 시작

1. Issue를 생성한다. (`.github/ISSUE_TEMPLATE`의 양식 사용)
2. 담당자를 지정한다.
3. 완료 조건을 작성한다.
4. Issue 번호를 기준으로 브랜치를 생성한다.

브랜치 예시:

```text
feature/124-season-ranking
fix/142-duplicate-title
refactor/151-resume-service
docs/160-adr-system
```

## 개발 중

1. 의미 있는 단위로 커밋한다.
2. 커밋 메시지는 [Conventional Commits 규칙](commit-convention.md)을 따른다.
3. 중요한 기술 판단이 생기면 [ADR](../adr/README.md) 작성 여부를 검토한다.
4. 비밀정보를 커밋하지 않는다.

## 기능 완료

1. 관련 Issue를 연결해 PR을 작성한다. (`Closes #번호`)
2. 변경 내용뿐 아니라 변경 이유를 작성한다.
3. 테스트 결과를 작성한다.
4. 중요 PR에는 [포트폴리오 관련 라벨](github-labels.md)을 붙인다.
5. 리뷰 후 병합한다.

## 매주

1. 병합된 PR을 확인한다.
2. 팀원별 주요 작업을 정리한다. ([주간 기록](../worklog/README.md))
3. 중요한 문제와 해결 과정만 기록한다(주당 1~3개).
4. 다음 주 작업과 도움이 필요한 부분을 공유한다.

## 프로젝트 종료

1. `portfolio` 라벨 PR을 수집한다.
2. 담당 범위를 확인한다.
3. ADR에서 기술 선택 이유를 가져온다.
4. Worklog에서 문제 해결과 협업 사례를 가져온다.
5. 성과를 검증한다(없는 수치를 만들지 않는다).
6. 공개할 수 없는 정보를 제거한다.
7. [포트폴리오 가이드](../portfolio/README.md)에 따라 최종 문서를 작성한다.

---

## 문서 작성 원칙

- 코드만 보면 아는 내용보다 **왜 변경했는지**를 기록한다.
- 확인되지 않은 성과 수치를 만들지 않는다.
- 남이 구현한 작업을 자신의 성과처럼 쓰지 않는다.
- 장점뿐 아니라 단점·한계도 기록한다.
- 같은 내용을 Issue/PR/ADR/Worklog에 길게 반복 복사하지 않는다. 문서 간에는 링크로 연결한다.
- 문서가 개발을 방해할 정도로 복잡해지지 않게 한다.
