[파일 구조]
- 라우트는 routes/, 비즈니스 로직은 services/, 외부 API는 external/, 공통 규약은 common/에 둔다.
- routes는 얇게 유지하고 실제 로직은 services 함수를 호출한다.
- models/ 와 common/ 은 공통 자산. 수정이 필요하면 먼저 알리고 함부로 바꾸지 마라.
- 화면은 templates/, 스타일은 static/css/pages/, JS는 static/js/pages/에 둔다.
- 새 템플릿은 {% extends 'layout.html' %} 상속.

[API 규칙]
- URL은 영어 명사 복수형: /api/experiences (조회 GET, 생성 POST, 수정 PUT, 삭제 DELETE)
- 응답은 항상 이 형식으로 통일한다:
  성공: { "success": true, "data": {...}, "error": null }
  실패: { "success": false, "data": null, "error": { "code": "대문자코드", "message": "한글메시지" } }
- 상태코드: 성공200 / 생성201 / 잘못된요청400 / 권한없음403 / 없음404 / 서버오류500
- API 응답의 success로 성공/실패 구분. 데이터 없을 때·로딩 중·오류 화면 처리 필수.

[코드 스타일]
- 클래스 PascalCase, 변수·함수 snake_case(Python)/camelCase(JS), 상수 UPPER_CASE, 들여쓰기 4칸
- 매직 넘버 금지: 숫자를 그냥 박지 말고 common/constants.py에 이름 붙여서 사용
- 비밀키·API키는 코드에 박지 말고 os.environ.get()으로 .env에서 읽는다
- 디버그 print·죽은 코드는 남기지 않는다
- 남의 데이터 수정·삭제 라우트엔 로그인·소유 확인을 넣는다
- 서버 데이터를 템플릿에서 JS로 넘길 땐 | tojson 사용
- 기존 재사용 가능한 함수가 있으면 새로 만들지 말고 그것을 써라

[완료 기준]
- 핵심 로직(회원가입·ESG·추천)이면 tests/에 테스트를 최소 1개 추가
- 작업 후 무엇을 왜 바꿨는지, 어떻게 테스트하는지 요약

[작업 방식]
- 코드를 수정하기 전에 "수정할 파일 목록 + 각 파일에서 할 일"을 먼저 제시하고 확인을 받아라.
- 기존에 재사용 가능한 함수가 있으면 새로 만들지 말고 그것을 써라.
- 답변은 한국어로.
