# FarmLink 팀 개발 규칙

> 모든 팀원이 코드 작성 전 반드시 읽어야 할 파일.
> Claude에게 작업을 요청할 때는 `docs/prompt_header.txt`를 매 요청 맨 위에 붙여 사용한다.

---

## 0. 핵심 단어 5개

| 단어 | 한마디로 | 설명 |
|------|---------|------|
| Git | 코드 전용 구글드라이브+되돌리기 | 여러 명이 같이 고치고 과거로 되돌림. GitHub에 올려 공유 |
| 브랜치 | 내 전용 작업 공간 | 원본(main) 복사해 그 위에서 작업. 실수해도 원본 안전 |
| 커밋 | 게임 세이브(저장) | 작업 저장. 저장할 때 "뭘 했는지 메모"를 남김 |
| PR | "합쳐도 돼요?" 신청서 | main에 바로 안 붙이고 확인받고 합침 |
| 머지 | 합치기 | PR 승인되면 main에 실제로 합쳐짐 |

전체 흐름: **브랜치 → 작업 → 커밋 → PR → 리뷰 → 승인 → 머지** (기능마다 반복)

---

## 1. 브랜치 규칙

| 브랜치 | 용도 | 예시 |
|--------|------|------|
| `main` | 안정 버전, 직접 push 금지 | — |
| `develop` | 개발 통합 브랜치 | — |
| `feature/기능명` | 새 기능 | `feature/user-signup` |
| `fix/버그명` | 버그 수정 | `fix/login-500` |
| `chore/작업명` | 설정·잡일 | `chore/gitignore-update` |

- 이름은 **소문자-하이픈** 형식. 사람 이름 ❌
- 이름만 봐도 무슨 작업인지 알 수 있게
- 머지 후 해당 브랜치 삭제

---

## 2. 커밋 메시지 규칙

형식: `타입: 무엇을 했는지`

| 타입 | 의미 | 예시 |
|------|------|------|
| `feat` | 새 기능 | `feat: 회원가입 API 구현` |
| `fix` | 버그 수정 | `fix: 로그인 세션 만료 오류 수정` |
| `refactor` | 기능 그대로, 코드 정리 | `refactor: 추천 점수 함수 분리` |
| `docs` | 문서 | `docs: API 명세 문서 추가` |
| `test` | 테스트 | `test: ESG 점수 테스트 추가` |
| `chore` | 설정·잡일 | `chore: gitignore에 build 추가` |

- 설명은 한글, 짧게, 명령형 ("~했음" ❌ / "~구현" ⭕)
- 한 커밋 = 한 가지 일 (섞지 말 것)
- 제목 50자 이내

| 구분 | 예시 |
|------|------|
| ✘ 나쁜 예 | `수정` · `ㅁㄴㅇㄹ` · `최종` · `진짜최종` |
| ⭕ 좋은 예 | `feat: 체험 예약 API 구현` · `fix: 예약 인원 0명 입력 방어` |

---

## 3. PR 규칙

- PR 하나 = 기능 하나, **300줄 이내**
- 본인 PR 본인 머지 금지 → 팀원 1명 승인 후 머지
- 요청 받으면 **24시간 안에** 리뷰
- 충돌은 올린 사람이 해결

**PR 설명 템플릿:**

```
## 무엇을
회원가입 API를 구현했습니다.

## 왜
사용자가 계정을 만들어야 예약으로 넘어갈 수 있어서.

## 어떻게 테스트했는지
- 정상 가입 성공 확인
- 중복 이메일 시 에러 응답 확인
- 빈 값 입력 시 400 응답 확인
```

## 4. 파일 구조

```
routes/       라우트 (얇게 유지, 실제 로직은 services 호출)
services/     비즈니스 로직
external/     외부 API 연동
common/       공통 규약·상수·응답 형식
models/       DB 모델
templates/    화면(Jinja2 템플릿)
static/css/   스타일
static/js/    JavaScript
tests/        테스트
docs/         문서
```

- `models/`와 `common/`은 공통 자산 — **수정 전 반드시 팀에 알리고 합의**
- 새 템플릿은 `{% extends 'layout.html' %}` 상속

## 5. API 규칙

### URL — 영어 명사 복수형 + HTTP 메서드

| 하는 일 | 메서드 | URL |
|---------|--------|-----|
| 목록 조회 | GET | `/api/experiences` |
| 하나 조회 | GET | `/api/experiences/5` |
| 생성 | POST | `/api/experiences` |
| 수정 | PUT | `/api/experiences/5` |
| 삭제 | DELETE | `/api/experiences/5` |

### 응답 형식 — 항상 통일

```json
// 성공
{ "success": true, "data": { ... }, "error": null }

// 실패
{ "success": false, "data": null,
  "error": { "code": "EMAIL_DUPLICATE", "message": "이미 가입된 이메일입니다" } }
```

| 항목 | 기준 |
|------|------|
| 상태코드 | 성공 200 / 생성 201 / 잘못된 요청 400 / 권한 없음 403 / 없음 404 / 서버 오류 500 |
| error.code | 영어 대문자 (`EMAIL_DUPLICATE`) |
| error.message | 사용자용 한글 |
| API 변경 시 | 준형(프론트)에게 즉시 공유 + 명세 문서 업데이트 |

## 6. 코드 스타일

| 대상 | 규칙 | 예시 |
|------|------|------|
| 클래스 | PascalCase | `User`, `ReservationService` |
| 변수·함수 (Python) | snake_case | `user_name`, `get_price()` |
| 변수·함수 (JS) | camelCase | `userName`, `getPrice()` |
| 상수 | UPPER_CASE | `MAX_PARTICIPANTS`, `ESG_THRESHOLD` |
| 들여쓰기 | 4칸 스페이스 | — |

**매직 넘버 금지**

```python
# ✘ 나쁜 예
if score > 80:

# ⭕ 좋은 예 — common/constants.py에 이름 붙이기
ESG_THRESHOLD = 80
if score > ESG_THRESHOLD:
```

**기타**

- 비밀키·API 키는 코드에 박지 말고 `os.environ.get()`으로 `.env`에서 읽기
- 디버그 `print`·죽은 코드는 남기지 않기
- 남의 데이터 수정·삭제 라우트엔 로그인·소유 확인 필수
- 서버 데이터를 템플릿에서 JS로 넘길 땐 `| tojson` 사용
- 기존 재사용 가능한 함수·컴포넌트가 있으면 새로 만들지 말고 그것을 사용

## 7. 코드 리뷰 체크리스트

### 백엔드 (건태·우성)

- [ ] 비밀키를 `.env`에서 읽나
- [ ] 남의 데이터 수정·삭제에 권한 확인 있나
- [ ] 에러를 통일 형식으로 응답하나
- [ ] 입력값 검사(빈 값·이상 값) 했나
- [ ] 디버그 출력·죽은 코드 지웠나
- [ ] 메서드가 한 가지 일만 하나
- [ ] 핵심 로직이면 테스트 있나

### 프론트 (준형)

- [ ] API 키를 화면에 하드코딩 안 했나
- [ ] 데이터 없을 때(빈 화면·오류) 처리했나
- [ ] 요소 쓰기 전 존재 확인했나
- [ ] 로딩 중 표시 있나
- [ ] 모바일에서 안 깨지나
- [ ] 공통 컴포넌트 재사용했나
- [ ] `success`로 성공/실패 구분하나

코멘트 쓰는 법: "고쳐" ❌ → 근거 한 줄 ⭕ ("검증+저장 두 가지를 하는 것 같아요. 분리하면 테스트하기 쉬울 듯요")

## 8. "완료"의 정의 (DoD)

| 단계 | 완료 기준 |
|------|---------|
| 기능 개발 | 의도대로 동작 (필수) |
| 핵심 로직 테스트 | 회원가입·ESG·추천처럼 틀리면 큰일 나는 것엔 테스트 1개 (필수) |
| 단순 CRUD 테스트 | 단순 조회·목록은 선택 (나중에) |
| 코드 정리 | 디버그·죽은 코드 삭제, 스타일 준수 |
| 리뷰 | PR 올려 팀원 1명 승인 |
| 기록 | 커밋 규칙대로, API 바뀌면 준형에게 공유 |

## 10. 파일 관리 (.gitignore)

| 제외할 것 | 이유 |
|---------|------|
| `build/` | 컴파일 자동 생성물 |
| `.env` | API 키·비밀번호 |
| `*.pyc`, `__pycache__/` | Python 컴파일 결과물 |
| `.idea/`, `.vscode/` | 에디터 개인 설정 |
| `uploads/` | 업로드 파일 (용량 큼, 서버에서 관리) |

- `.env` 커밋 절대 금지
- 키 유출 시 → 해당 키 즉시 폐기하고 새로 발급
- `.env.example`에 키 이름만 남기고 값은 비워서 공유
